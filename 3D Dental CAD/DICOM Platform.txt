Your main change is to remove the webhook-based save workflow for drawings and annotations. Instead, you want a user-controlled Save workflow: a QC reviewer or designer opens a 3D preview, uses the markup tools, and explicitly clicks Save to persist the work to your database.

The key architectural distinction is:

- While editing: keep changes in browser-local state, with optional local persistence for recovery.
- When Save is clicked: send the complete annotation state to your backend through an authenticated API and persist it in PostgreSQL.
- When the preview is reopened: load the last successfully saved version.
- Redis: use it only if you need shared caching, temporary drafts across devices, or collaboration infrastructure. It is not required just to implement a Save button.

You can retain your existing Next.js, React Three Fiber, PostgreSQL, and Redis stack. The asset-ingestion pipeline for dental ZIP files can remain separate; the change applies to the markup and annotation persistence workflow.

Here is the revised implementation specification. It replaces automatic webhook-based drawing persistence with an explicit Save action, while keeping the 3D preview, markup tools, and dental asset-processing workflow intact.

# 3D Dental CAD/DICOM Platform — Explicit Save Architecture

**Document Version:** 2.0\
**Scope:** 3D Preview, QC Review, Designer Markup, Annotation Persistence\
**Existing Stack:** Next.js App Router, React, React Three Fiber, Three.js, PostgreSQL, Redis\
**Primary Requirement:** No webhook-based saving for user drawings or markup.

## 1. Objective

Implement a user-controlled save system for the 3D dental preview.

A QC reviewer or designer must be able to:

1. Open a dental case and view its 3D model.
2. Select markup tools, draw annotations, add measurements, and modify existing drawings.
3. Continue editing without immediately writing every change to the database.
4. Click **Save** to persist all current changes to the backend.
5. Reopen the preview later and retrieve the last successfully saved state.
6. Recover unsaved changes after an accidental refresh or browser crash, where browser storage permits.

The application must clearly distinguish between unsaved local changes and saved database state.

## 2. Revised Architecture

### Technology responsibilities

| Component                    | Responsibility                                                         |
| ---------------------------- | ---------------------------------------------------------------------- |
| Next.js / React              | Preview UI, markup tools, Save and Discard actions                     |
| React Three Fiber / Three.js | 3D rendering and annotation geometry                                   |
| Browser state                | Immediate editing state                                                |
| IndexedDB                    | Optional durable local draft recovery                                  |
| Next.js API                  | Authentication, validation, and save/load operations                   |
| PostgreSQL                   | Authoritative storage for saved annotations and versions               |
| Redis                        | Optional shared draft cache, collaboration support, or temporary state |
| Cloudflare R2 / CDN          | Original and processed dental assets                                   |

**Important:** PostgreSQL is the source of truth for saved work. Redis must not be the only place where confirmed saves are stored.

## 3. User Workflow

### Step 1 — Open the 3D preview

When a user opens a case:

- Fetch the case's 3D asset URLs and metadata.
- Load the saved annotation document from the backend.
- Render the model and saved markup in the 3D viewport.
- Initialize the local editing state using the loaded saved document.
- Record the current saved revision number.

If no saved annotations exist, initialize an empty annotation document.

### Step 2 — Edit markup

The user can use supported tools, including:

- 3D surface brush and freehand markup.
- Lines, points, and measurement tools.
- Text and comment pins.
- Annotation selection and deletion.
- Layer creation, reordering, visibility, locking, and opacity.
- Undo and redo.
- Existing supported camera and viewing controls.

All drawing interactions must update the local editing state immediately.

Do not call the save API for every pointer event, brush point, or layer adjustment.

### Step 3 — Maintain the local draft

During editing:

- Keep the current annotation document in React state or a suitable client-side state store.
- Update the 3D scene immediately as the user edits.
- Mark the document as dirty when its persistable contents change.
- Optionally persist the draft to IndexedDB using a debounced local write.
- Keep browser persistence separate from the confirmed database state.

Use IndexedDB rather than relying exclusively on localStorage for substantial annotation documents. localStorage can be used for small preferences or compact draft metadata.

Local drafts should be scoped to the user, case, and annotation document. Never store authentication tokens or sensitive patient data unnecessarily in browser storage.

### Step 4 — Explicit Save

Display a Save button in the preview interface.

When the user clicks Save:

1. Disable duplicate submissions while the request is in progress.
2. Capture a consistent snapshot of the current annotation document.
3. Include its case ID, document ID, expected saved revision, and schema version.
4. Submit the snapshot through an authenticated HTTPS API request.
5. Validate the request on the backend.
6. Persist the complete new document or its changes in PostgreSQL within a database transaction.
7. Increment the saved revision and record the save metadata.
8. Return the new revision and save timestamp.
9. Mark the submitted snapshot as saved.
10. Update the UI to show a successful save.

Show these UI states:

- **Saved** — no unsaved changes remain.
- **Unsaved changes** — the current document differs from the saved version.
- **Saving…** — a save request is in progress.
- **Save failed** — the backend did not confirm persistence.

Do not show a successful save message until the database transaction has committed.

If the user continues drawing while a save is in progress, preserve those newer changes as unsaved. A successful response for an earlier snapshot must not incorrectly mark newer edits as saved.

### Step 5 — Reopen the preview

When the user opens the same case again:

- Load the latest confirmed database revision.
- Restore the saved annotation geometry and layer configuration.
- Reconstruct the 3D markup against the correct model and coordinate system.
- Restore the appropriate visibility, opacity, and other persisted tool settings.
- Allow editing to resume.

If an unsaved local draft exists, offer the user an explicit option to recover it when it is compatible with the saved revision. Do not silently overwrite newer server data with an old local draft.

## 4. Frontend Implementation

Create or update a dedicated annotation document state manager.

Suggested state:

```
type SaveStatus =
  | "saved"
  | "dirty"
  | "saving"
  | "error";

interface AnnotationDocument {
  id: string;
  caseId: string;
  schemaVersion: number;
  revision: number;
  layers: AnnotationLayer[];
  updatedAt?: string;
}

interface EditorState {
  document: AnnotationDocument;
  saveStatus: SaveStatus;
  lastSavedRevision: number;
  lastSavedAt?: string;
  saveError?: string;
}
```

Define `AnnotationLayer` and the annotation geometry types according to the actual markup tools in the existing application.

The editor must support these operations:

- `loadDocument()`
- `updateAnnotation()`
- `addAnnotation()`
- `deleteAnnotation()`
- `updateLayer()`
- `undo()`
- `redo()`
- `saveDocument()`
- `discardChanges()`
- `recoverLocalDraft()`

All editing tools must use the same document state manager. Avoid separate, disconnected state stores for each tool that can cause annotations to disappear during saving or switching layers.

### Dirty-state handling

Use a reliable document revision or change-tracking mechanism.

When an edit occurs, the editor becomes dirty. When a save succeeds, mark only the snapshot that was submitted as saved.

Do not rely solely on pointer events or UI button states to determine whether a document is saved.

### Navigation protection

If unsaved changes exist and the user attempts to:

- Close the preview.
- Navigate to another case.
- Refresh the page.
- Exit the editor.

Warn them before discarding unsaved work. Use browser lifecycle events as a best-effort safeguard, not as a substitute for local draft persistence.

## 5. Backend API

Implement authenticated endpoints for annotation documents.

### Load annotations

`GET /api/cases/:caseId/annotations`

Return the latest saved document, its revision, and its metadata.

If the document does not exist, return a clear empty-document response or a documented not-found response that the frontend handles consistently.

### Save annotations

`PUT /api/cases/:caseId/annotations/:documentId`

Request example:

```
{
  "schemaVersion": 1,
  "expectedRevision": 4,
  "layers": [],
  "saveReason": "manual"
}
```

The `layers` array above is illustrative. The production request must contain the actual validated annotation and layer data.

The backend must:

1. Authenticate the user.
2. Verify access to the case and document.
3. Validate the payload size, structure, types, and coordinate values.
4. Check `expectedRevision` against the current saved revision.
5. Persist the new document transactionally.
6. Increment the revision.
7. Return the committed revision and timestamp.

Example successful response:

```
{
  "success": true,
  "documentId": "document-id",
  "revision": 5,
  "savedAt": "2026-10-24T15:30:00.000Z"
}
```

A revision conflict must return an appropriate conflict response, such as HTTP 409, rather than silently overwriting another user's newer work.

### Optional discard endpoint

Implement a server-side discard operation only if the application needs to manage shared drafts. For a purely local unsaved draft, discard can be handled on the client by restoring the last saved document.

Discarding a local draft must never delete a previously saved database version.

## 6. PostgreSQL Data Model

Use the following logical schema. Adapt table and column names to the existing database conventions.

### `annotation_documents`

- `id` — document primary key.
- `case_id` — associated dental case.
- `revision` — monotonically increasing saved revision.
- `schema_version` — annotation document format version.
- `document_data` — validated JSONB annotation document, or a suitable normalized representation.
- `created_by` — creator.
- `updated_by` — last saver.
- `created_at` — creation timestamp.
- `updated_at` — last successful save timestamp.

Enforce the appropriate case/document relationships and authorization rules.

Use a uniqueness constraint for the intended document identity, such as the case and document ID combination.

### Optional `annotation_versions`

For recoverability and audit history, store previous committed revisions separately:

- `id`
- `document_id`
- `revision`
- `document_data`
- `saved_by`
- `saved_at`

Each successful manual save can create a new immutable version. Apply a retention policy appropriate to the application's clinical and operational requirements.

The current document and its version record should be updated within the same transaction when version history is enabled.

## 7. Redis: Optional, Not Required for Manual Save

Do not introduce Redis as a mandatory step between the Save button and PostgreSQL.

For the initial implementation, the recommended flow is:

**Save button → authenticated Next.js API → PostgreSQL transaction → success response.**

Use Redis only when there is a defined requirement, such as:

- Shared temporary drafts across application instances.
- Multi-user collaboration.
- Short-lived coordination state.
- Cacheable reads with explicit invalidation.
- WebSocket presence and transient cursor events.

If Redis is introduced for draft caching, define TTLs, eviction behavior, recovery rules, and the distinction between cached and committed data.

A Redis write alone must never be treated as a successful permanent save.

## 8. Webhooks and Real-Time Communication

Remove webhook triggers from the annotation Save workflow.

Saving a markup document must not require:

- A third-party webhook.
- A background webhook callback.
- A webhook confirmation before the UI can show success.
- A Redis Pub/Sub event solely to persist the manual save.

A normal authenticated API request is sufficient.

WebSockets and Yjs may remain as separate, optional capabilities if simultaneous collaborative editing is required. They are not necessary for a single-user manual-save workflow.

If collaboration is enabled later, define how multiple users' edits merge and how explicit saves interact with concurrent revisions. Do not assume that local snapshots alone provide safe multiplayer conflict resolution.

The dental ZIP ingestion pipeline may continue to use background workers or event-driven processing where needed. That pipeline is separate from saving annotation documents.

## 9. Reliability and Security Requirements

- Authenticate all save and load operations.
- Verify case-level and document-level permissions on every request.
- Enforce request size limits and validate every annotation.
- Use parameterized database operations and transactions.
- Prevent lost updates with revision checks.
- Make retries safe, including handling a timeout after a database commit.
- Preserve local edits if the server is unavailable.
- Never report a save as successful when persistence is uncertain.
- Avoid logging raw patient information or sensitive annotation contents.
- Keep patient-identifiable data out of unnecessary browser caches.
- Define retention, access logging, backup, and audit requirements for clinical records.
- Ensure local drafts cannot be restored into the wrong case or user session.

## 10. Testing Requirements

### Frontend

- Drawing changes the 3D scene immediately.
- Drawing does not trigger a database save request.
- Clicking Save submits the current annotation document.
- Multiple rapid clicks do not create duplicate or conflicting saves.
- Editing during an in-flight save leaves newer changes marked unsaved.
- Failed saves preserve the current drawing.
- Reload recovery works when a valid local draft exists.
- Discard restores the last saved snapshot without deleting it.
- Undo and redo update the document and dirty state correctly.

### Backend

- Valid saves persist to PostgreSQL.
- Unauthorized users cannot read or modify a case.
- Invalid annotation payloads are rejected.
- Revision conflicts return HTTP 409.
- A failed transaction does not partially update the document.
- Retried requests do not create unintended duplicate versions.
- Reloading after a confirmed save returns the saved data.
- Concurrent saves cannot silently overwrite newer revisions.

### End-to-end acceptance test

1. Open a dental case and its 3D preview.
2. Draw three annotations using the markup tools.
3. Verify that no save API call occurs while drawing.
4. Click Save.
5. Verify that the save API is called once and the database revision increments.
6. Refresh the browser.
7. Reopen the case.
8. Verify that all three annotations appear in the correct locations.
9. Draw another annotation, simulate a network failure, and verify that the unsaved work remains available.
10. Restore connectivity, save again, refresh, and verify persistence.

## 12. Definition of Done

The implementation is complete when:

- Designers and QC reviewers can edit the 3D preview without continuously writing annotations to the database.
- Clicking Save is the explicit action that commits their current changes.
- A confirmed save is durable in PostgreSQL.
- Reopening the case restores the most recently saved annotation document.
- Failed saves do not erase the user's work.
- Concurrent changes cannot silently overwrite newer saved data.
- Webhooks are not required for annotation persistence.
- Redis remains optional for this workflow.
- Existing dental asset ingestion and rendering continue to function.

**Final architectural decision:** Keep editing local, persist explicitly through a normal authenticated API, and use PostgreSQL as the authoritative saved state. Add IndexedDB for local recovery and Redis only when a concrete caching or collaboration requirement justifies it.

One implementation detail is especially important: if multiple designers or QC reviewers can edit the same case, use revision checks and conflict handling from the beginning. Otherwise, one person's Save action could overwrite another person's annotations.

Yes — you can build this system with very high accuracy and a fast user experience. However, 100% accuracy and zero latency cannot be guaranteed in a real-world application, especially one involving 3D dental models, medical imaging, browser storage, and database persistence.

The right goal is to make the system precise, responsive, fault-tolerant, and verifiably correct.

## 1. What accuracy and performance can you achieve?

| Area                   | Practical target                                              | How to achieve it                                                              |
| ---------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 3D markup accuracy     | Deterministic geometry within defined tolerances              | Correct raycasting, coordinate transforms, mesh alignment, and numerical tests |
| Drawing responsiveness | Immediate local rendering                                     | Update the Three.js scene locally without waiting for the backend              |
| Save reliability       | No acknowledged save without a committed database transaction | PostgreSQL transactions, revision checks, and reliable retry handling          |
| Reopening saved work   | Restore the last confirmed revision exactly                   | Validated serialization and round-trip tests                                   |
| Concurrent editing     | Detect conflicting updates                                    | Optimistic concurrency control or a properly designed collaboration system     |
| Local recovery         | Recover drafts after many refreshes or crashes                | IndexedDB, versioned drafts, and recovery tests                                |
| 3D preview performance | Target 50–60 FPS on supported hardware                        | Level of detail, optimized geometry, demand rendering, and GPU profiling       |

These are engineering targets, not guarantees. In particular, a 50–60 FPS target depends on model complexity, GPU capability, browser, and device memory.

## 3. Five rules that make the system reliable

1. Never block drawing on the network. Raycasting, visual feedback, and annotation updates should happen locally. A slow API must not freeze the 3D editor.
2. Save immutable snapshots. If a user continues drawing during a save, the newer edits must remain dirty until they are saved too.
3. Confirm only committed saves. A timeout does not prove that the database write failed. Use an idempotency key or equivalent retry strategy to avoid duplicate versions.
4. Protect against overwrites. Save with an expected revision. If another user has saved a newer version, return a conflict instead of silently overwriting their work.
5. Validate clinical geometry separately. Test model alignment, units, coordinate systems, surface placement, and measurement tolerances using calibrated reference models. A technically successful save does not prove that a measurement is clinically accurate.

## 4. What about speed?

The most important optimization is separating interactive editing from database persistence.

- Drawing should feel immediate because the browser renders changes without waiting for PostgreSQL.
- Local draft writes can be debounced so that every brush movement does not cause excessive storage work.
- A manual save should submit a compact, validated document rather than the entire 3D model.
- Large original meshes and DICOM assets should remain in object storage/CDN; save only annotation data and the necessary references.
- Profile the editor using realistic high-resolution dental models and lower-end laptops, not only a developer workstation.

The actual Save response time depends on payload size, network conditions, database load, and deployment location. Set a measurable latency objective after benchmarking the expected workload.

## 5. How we should verify the result

I would define acceptance criteria before implementation:

- Drawing: no network dependency for immediate visual feedback.
- Persistence: every acknowledged save survives a page reload and a fresh database read.
- Integrity: saved annotations reproduce their original geometry and units within specified tolerances.
- Concurrency: stale writes are rejected or resolved explicitly.
- Recovery: unsaved work can be recovered from a valid local draft.
- Performance: meet defined frame-rate and API latency targets on representative hardware.
- Testing: automated round-trip, failure-injection, concurrent-save, and end-to-end tests.

My recommendation is to build the manual-save workflow first, test it thoroughly, and then add multiplayer synchronization only if your product requires simultaneous editing.

Bottom line: You can make the experience extremely fast and the persistence process highly reliable. The strongest design is immediate local editing, IndexedDB-based recovery, explicit saves to PostgreSQL, and strict revision control. That gives you a practical path toward near-perfect data integrity without sacrificing the responsiveness of the 3D preview.
